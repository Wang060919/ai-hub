# AI Hub 项目总规划与项目边界说明

## 1. 项目定位

AI Hub 是一个面向学习与个人工作流的桌面 AI 智能中枢。

它的长期方向不是单点聊天工具，而是一个可以持续扩展能力、连接学习场景与个人生产力场景的统一中枢。不过在当前阶段，项目并不直接追求完整的 Personal AI OS 落地，而是从一个可运行、可扩展、可交接的 FastAPI Skill 网关开始。

当前 8 天冲刺的目标，是先证明这条架构路线成立，并建立后续 Claude Code、Codex、Gemini 可持续接力的开发基线。

## 2. 核心愿景

AI Hub 的长期愿景保留如下方向，但这些内容不默认进入当前阶段开发范围：

- PC 桌面 AI 智能中枢
- 插件化 Skill 网关
- 面向英语学习与长期知识积累的伴学能力
- 面向个人工作流的生产力支持
- 从被动问答逐步演进到主动协作
- 最终具备桌面端、自动化、多模态与设备联动能力

换句话说，愿景不删减，但节奏必须收敛。当前阶段先做后端微核心，后续再逐步叠加 AI、自动化、多模态和桌面表现层。

## 3. 架构原则

### 3.1 微核心 + Skill 插件

AI Hub 采用“FastAPI 微核心 + Skill 插件化网关”架构。

- 微核心负责统一入口
- Skill 负责具体能力实现
- 能力之间尽量解耦，便于独立迭代与替换

### 3.2 中枢职责边界

中枢本身不承载复杂业务逻辑，它主要负责：

- 协议定义
- 请求路由
- 状态聚合
- 统一返回格式
- 基础异常处理

具体能力由各个 Skill 独立实现，例如：

- EchoSkill 负责回显
- TimeSkill 负责时间查询
- IdeaCaptureSkill 负责灵感记录
- DifyEnglishSkill 负责四级英语助手能力

### 3.3 先证实架构，再扩展能力

当前阶段优先验证：

- 网关是否能稳定接收请求
- Router 是否能正确分发到 Skill
- Skill 接口是否足够统一
- JSON 协议是否足够清晰
- SQLite 是否能支撑轻量数据沉淀

只有这些基础成立，后面再接入 Dify、本地模型、OpenClaw、桌面端，才不会反复返工。

## 4. 全局数据流

AI Hub 当前推荐的数据流如下：

1. 用户输入
2. 前端 / 命令行 / 外部接口
3. FastAPI Gateway
4. Router
5. Skill
6. 统一 JSON 返回

可以进一步理解为：

- 用户从命令行、前端或其他接口提交请求
- FastAPI Gateway 接收并校验请求
- Router 根据规则将请求分发给对应 Skill
- Skill 独立执行具体逻辑
- 系统返回统一 JSON 响应，便于前端、测试和后续自动化接入

这一数据流在 V0.1 阶段必须保持简单、稳定、可验证。

## 5. 当前阶段功能边界

### 5.1 V0.1 边界

V0.1 只做最小可运行闭环，不扩展新功能。

V0.1 仅包含：

- FastAPI 微核心
- `/chat` 接口
- BaseSkill
- EchoSkill
- TimeSkill
- IdeaCaptureSkill
- SQLite 灵感盲存

V0.1 的重点不是“智能程度”，而是“架构成立”和“闭环可运行”。

### 5.2 V0.2 边界

V0.2 的首要任务是接入已有 Dify 四级英语助手，形成真实 AI 学习闭环。

V0.2 的重点是：

- DifyEnglishSkill
- Dify API 接入
- 查词、出题、判题、错词整理
- 学习记录与错误处理

V0.2 不应把 Ollama 或本地模型路由放在优先级最前面。

## 6. 延后功能

以下能力全部保留为后续阶段规划，但不进入当前 8 天冲刺范围：

- Ollama
- 本地模型路由
- OpenClaw
- Docker 沙盒
- OCR
- Tauri 桌面端
- Live2D
- ChromaDB
- GraphRAG
- Always-On 能力
- IoT 联动

这些方向有明确价值，但如果提前压进 V0.1 或 8 天实施计划，会直接稀释核心闭环，增加环境配置、依赖管理和调试复杂度。

## 7. 硬件与环境约束

当前已知用户电脑环境：

- CPU：i7-14650
- GPU：RTX 4060
- 内存：16GB

在这个条件下，8 天冲刺期不优先部署本地 7B/8B 模型，也不优先推动复杂本地模型路由，原因很明确：

- 环境配置耗时高
- 显存与内存调优成本高
- 容易被 Ollama、量化模型、驱动和依赖问题拖慢节奏
- 会挤压核心后端闭环开发时间

因此，当前策略是：

- 先做规则路由
- 先做 Dify 接入
- 本地模型路由后置到 V0.3

## 8. 简历价值

这个项目的简历价值并不依赖“一次性做完所有愿景”，而依赖于分阶段展示清晰的系统能力。

当前和后续可形成的高价值亮点包括：

- FastAPI 插件化架构
- 统一 Skill 网关设计
- Dify RAG / 工作流接入
- SQLite 数据沉淀与轻量状态管理
- 为后续 OpenClaw + Docker 安全自动化预留架构接口

这意味着即使当前只完成 V0.1 与部分 V0.2，也依然可以形成一个结构完整、技术路线清晰、扩展性明确的项目叙事。

为了服务后续 Claude Code、Codex、Gemini 接力开发，三份核心文档的优先级必须明确如下：

1. `AI_Hub_Version_Roadmap.md`
2. `AI_Hub_Implementation_Plan.md`
3. `AI_Hub_Project_Planning.md`

含义如下：

- 版本路线图负责定义阶段边界与优先级

- 总规划文档负责保留愿景、架构原则与边界说明

若三者出现冲突，应以版本路线图优先，再由实施规划书约束当前开发范围。
