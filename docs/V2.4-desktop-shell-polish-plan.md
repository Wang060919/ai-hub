## 1. 当前 UI 问题

### 1.1 顶部栏 (Topbar) 是典型的 Web 管理后台导航

当前 `index.html` 的 `.cf-topbar` 包含后端地址输入框、检查后端按钮、状态 Pills（后端地址、模型、状态），以及"经典首页"链接。这是标准的 Web 后台管理系统导航栏模式——管理员在这里配置后端、检查连接、查看系统状态。桌面聊天软件的用户不应在首页看到这些。这些开发/调试信息应当迁移到独立的"状态/设置"页面。

### 1.2 所有内容包裹在固定宽度容器内，桌面窗口空间浪费严重

`.cf-shell` 设置了 `max-width: 1320px` 并水平居中。聊天区域内部又设置了 `max-width: 960px`。结果就是窗口边缘有大片空白，UI 浮在中间，像网页嵌入 Tauri 窗口，而不是原生桌面应用填满窗口。

### 1.3 左侧抽屉 (Drawer) 放的是调试面板，不是功能导航

左侧 `.cf-drawer`（340px）的内容是：后端状态面板、知识库面板（含摘要、搜索、接入、问答）、文件预览面板、聊天工作区助手面板。这些本质上是调试工具和高级管理操作，全部堆在聊天页面的抽屉里。桌面应用的标准做法是：用侧边栏做功能导航（聊天/文件/知识库/设置），而不是把调试面板塞在聊天抽屉里。

### 1.4 上下文栏 (Context Bar) 向用户暴露内部技术细节

聊天区顶部的上下文栏展示"模式：聊天"、"后端：未检查"、"历史：0/4 轮"、"仅手动操作"、"无自动文件上传"——这些属于开发时的安全说明和技术状态，不应该占据聊天页面的核心视觉空间。桌面应用的聊天界面应当干净，只保留聊天需要的信息。

### 1.5 页脚 (Footer) 是 Web 应用模式

底部状态栏显示连接状态点 + "空闲/已连接"。桌面应用通常不在页脚放置此类信息，状态应通过系统托盘、标题栏或设置页面表达。

### 1.6 整体可滚动，缺乏桌面应用的独立滚动区域

整个 `body` 作为一个滚动容器，页眉、聊天区、页脚一起滚动。桌面应用的标准做法是固定壳层（sidebar + header），仅内容区独立滚动。

### 1.7 副标题"聊天优先核心候选版"传递未完成感

`.cf-topbar__subtitle` 显示"聊天优先核心候选版"，给用户的印象是这是实验性/候选版本，而非正式产品。

## 2. 推荐信息架构

```
AI Hub Desktop
├── 💬 聊天 (Chat)         ← 默认首页
├── 📁 文件 (Files)        ← 文件浏览器 & 预览
├── 📚 知识库 (Knowledge)  ← 知识库管理 & 搜索 & 问答
└── ⚙ 状态 (Status)       ← 后端地址配置、连接检查、系统状态
```

### 功能归属原则

| 功能 | 当前位置 | 目标位置 | 理由 |
|---|---|---|---|
| 聊天对话 + 模式切换 | 主区域 | 聊天页 (默认) | 核心功能，首页 |
| 后端地址输入 | 顶栏 | 状态页 | 配置项，非聊天功能 |
| 检查后端 | 顶栏 + 抽屉 | 状态页 | 管理操作 |
| 后端状态摘要 | 抽屉 | 状态页 | 调试信息 |
| 知识库摘要统计 | 抽屉 | 知识库页 | 属于知识库功能 |
| 知识库搜索/接入/问答 | 抽屉折叠 | 知识库页 | 完整功能页 |
| 文件预览 + 总结 | 抽屉 | 文件页 | 完整功能页 |
| 聊天工作区助手 | 抽屉 | 删除/合并到聊天 | 冗余 UI |
| 上下文栏 (模式/后端/历史) | 聊天区头 | 删除或缩简 | 技术细节 |
| 页脚连接状态 | 页脚 | 状态页 | 不属于聊天 |

## 3. 推荐页面结构

### 3.1 整体 Shell 布局

```
┌─────────────────────────────────────────────────┐
│ ┌──────────┐ ┌─────────────────────────────────┐│
│ │          │ │  Chat Header (minimal)           ││
│ │ Sidebar  │ │                                  ││
│ │          │ ├─────────────────────────────────┤│
│ │  💬 聊天  │ │                                  ││
│ │  📁 文件  │ │  Main Content Area              ││
│ │  📚 知识库│ │  (fills remaining space)        ││
│ │  ⚙ 状态  │ │  overflow-y: auto               ││
│ │          │ │                                  ││
│ │          │ ├─────────────────────────────────┤│
│ │          │ │  Composer (chat page only)       ││
│ └──────────┘ └─────────────────────────────────┘│
└─────────────────────────────────────────────────┘
```

关键约束：
- Shell 填满整个 Tauri 窗口（`100vw × 100vh`），无外部 margin/padding 浪费
- Sidebar 固定宽度（收起态 64px，展开态 200px），Full height
- 主内容区填满剩余空间，内部自滚动
- 无全局页脚
- 无外部 max-width 约束

### 3.2 Sidebar 设计

```
┌──────────┐
│ 🏠 AI Hub │  ← App icon + name (可点回聊天)
│──────────│
│ 💬 聊天   │  ← 当前激活态高亮
│ 📁 文件   │
│ 📚 知识库 │
│ ⚙ 状态   │
│          │
│          │
│          │
│          │
│──────────│
│ ⚡ v1.0  │  ← 小字版本号（可选）
└──────────┘
```

特性：
- 收起/展开切换（默认展开）
- 每个入口点击后主区域整体切换为对应页面（不是开抽屉，是全量替换主区域内容）
- 后端连接状态可以用极小图标（绿点/灰点）在 Sidebar 底部示意

### 3.3 聊天页 (默认首页)

主区域顶部：极简标题栏（"AI Hub" + 聊天/知识库模式切换 toggle）
主区域中间：消息列表（独立 scroll，填满剩余高度）
主区域底部：消息输入框 + 发送按钮（固定在底部，不随消息滚动）

**不再展示的内容：**
- 后端地址输入（移到状态页）
- 检查后端按钮（移到状态页）
- 状态 Pills（移到状态页）
- 上下文栏的技术细节（删除；保留模式标签在 header 中最简表达）
- 安全/隐私声明（删除，或在设置页展示）
- 聊天工作区助手面板（删除）
- 页脚连接状态（删除）

### 3.4 文件页

- 文件列表/树（左侧或上方）
- 文件预览区（右侧或下方）
- 文件总结按钮 + 结果区
- 复用现有 `files.js` 的 API 调用逻辑，重新组织 UI

### 3.5 知识库页

- 知识库状态摘要（文件数、分片数、FTS 状态）
- Tab 或分区：搜索 | 接入笔记 | 批量接入目录 | 问答
- 复用现有 `knowledge.js` 的全部逻辑，重新组织 UI 为独立页面布局

### 3.6 状态页

- 后端地址配置（输入框 + 保存/检查按钮）
- 连接状态（在线/离线、版本、技能数）
- 后端健康详情
- 知识库摘要（只读，快速一览）
- 不再需要文件预览在此页

## 4. 推荐视觉方向

### 4.1 填满窗口
- Shell: `width: 100vw; height: 100vh; overflow: hidden;`
- 主内容区: `flex: 1; overflow-y: auto;`
- Sidebar: 固定宽度，`height: 100vh;`

### 4.2 减少"卡片套卡片"
- 当前 `.cf-window` → `.cf-layout` → `.cf-chat` → `.cf-chat__workspace` 多层嵌套
- 改为：Shell → Sidebar + 主内容区 扁平两层

### 4.3 颜色与材质
- 保留现有蓝色系色调（已有设计资产）
- Sidebar 使用半透明玻璃效果（`backdrop-filter: blur()`）
- 主内容区使用实色背景
- 可后续考虑跟随系统 dark/light 模式

### 4.4 去 Web 化细节
- 移除页面中的 `<a>` 跳转链接（经典首页链接）
- 所有操作在单页内完成，无页面跳转
- 滚动条样式可定制为更细/更淡（匹配桌面应用风格）

## 6. 不要动的范围

### 绝不修改
- **所有后端代码** (`backend/` 下一切) —— 用户明确要求不新增后端功能、不改 API 协议
- **所有 API 调用模块** (`frontend/public/js/api/*.js`) —— 不改协议，只重用
- **核心工具模块** (`frontend/public/js/core/*.js`) —— markdown 渲染、工具函数等
- **UI 组件模块** (`frontend/public/js/ui/*.js`) —— status、loading、error 显示
- **目录模块** (`frontend/public/js/catalog/*.js`) —— file-tools-catalog
- **Orbit Icon 组件** (`frontend/public/js/components/orbit-icon.js`)
- **经典首页** (`index-classic.html` + `app.js` + `styles.css`) —— 保持浏览器兼容模式
- **Tauri Rust 代码** (`src-tauri/src/`) —— 不碰 Rust
- **构建脚本** (`frontend/build.mjs`, `frontend/server.mjs`)
- **原型目录** (`frontend/public/prototypes/`)

### 警惕过度设计
- 不要引入前端框架（继续 vanilla JS）
- 不要引入构建工具链变化（继续现有 ES module + 构建脚本）
- 不要做路由库（4 个页面，简单的显示/隐藏切换足够）
- 不要做动画库（CSS transition 足够）
- 不要做响应式断点重设计（桌面应用固定窗口，保留基本移动端降级即可）
- 不要做主题系统（先保持 light mode）
- 不要做 i18n
- 不要做拖拽、快捷键、系统托盘、全局快捷键

## 7. 执行策略（已修正）

### 修正说明

原规划建议 Round 1 先建空壳占位，后续轮次再迁移功能。此策略已废止。

**修正原因：** AI Hub 已完成 V2.1（chat-first 首页）、V2.2（classic 功能迁移）、V2.3（Tauri MVP），当前聊天、文件、知识库、状态检查功能全部可用。V2.4 不是从零做 UI，而是把现有功能重新组织成桌面软件结构。分轮次做会导致功能短暂退化。

**新策略：一轮完成。** 在一个 commit 内完成：
1. Shell 结构重构（sidebar + main area）
2. 所有 4 个页面功能完整迁移
3. 每个页面打开即可用，无占位内容

### 执行步骤

1. **创建分支** `feature/v2.4-desktop-app-shell-polish`
2. **重写 `index.html`** — 新的桌面 Shell DOM 结构，包含完整的 4 个页面内容
3. **重写 `chat-first.css`** — 桌面 Shell 布局 + 保留组件样式
4. **重写 `chat-first-shell.js`** — 简化为页面路由 + 连接指示器
5. **重写 `chat-first.js`** — 重新编排所有模块，完整迁移所有功能
6. **必要时微调子模块** — chat.js, files.js, knowledge.js, panel.js 做最小调整
7. **构建验证** — `npm run build`, `node --check`
8. **提交** — `feat: polish desktop app shell`
